# 오디오 구현·검증 기록

2026-09-12 · 개발 진행 중 · **NOT READY**

아래는 오디오 기능·UI 후보의 기록입니다. 이후 패킷 시계 보정과 원인 분리 결과, 최신 후보의 실패 항목은 [오디오 시계 수정 기록](11-audio-clock-investigation.md)을 따릅니다. 아래 코드 설명과 검증 수치는 당시 후보에 대한 증거로 보존합니다.

마이크·시스템 소리의 별도 원본 저장, 편집 구간에 따른 믹싱, 편집기 재생, AAC를 포함한 MP4 저장을 구현했습니다. 실제 녹음의 음질 검사에는 실패가 남아 있습니다. [G00~G11](04-production-readiness.md), [M01~M11](07-two-mode-release-gates.md), [UI 모션 기준](08-ui-motion.md)을 낮추지 않으며, 아래 짧은 검사는 G04 인증을 대신하지 않습니다.

## 수집·저장

- 두 모드의 녹화 준비에서 마이크와 시스템 출력 장치를 각각 선택합니다. 기본은 두 트랙 모두 꺼짐입니다. 시스템 소리는 선택한 출력 장치의 WASAPI loopback이며, 발표 소리를 회의 앱으로 전달하는 기능과 별개입니다. 장치 ID를 고정하고 녹화 중 다른 기본 장치로 자동 전환하지 않습니다.
- WASAPI shared mode에서 48 kHz 스테레오 float를 받아 각 트랙의 PCM16 WAV로 저장합니다. 패킷은 `GetBuffer`와 `ReleaseBuffer` 사이에서 복사하며, 패킷 소유권을 반환한 뒤 보간·쓰기 작업을 수행합니다. [Microsoft GetBuffer 문서](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer), [loopback 문서](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording).
- 영상과 같은 시작·일시정지·재개·종료 QPC를 오디오 시간축에 기록합니다. 가림·일시정지 구간은 PCM에서 제외하고, 활성 구간만 일시정지가 제거된 프로젝트 시간으로 매핑합니다. 패킷의 QPC 경계에서 선형 보간하여 출력 48 kHz 격자에 배치합니다. 이는 현재의 동기화 구현이며, 장시간 드리프트와 음질에 대한 인증된 리샘플러가 아닙니다.
- 파일당 최대 5초입니다. WAV 헤더·내용을 완성하고 flush·닫기를 마친 다음 오디오 저널을 확정합니다. 영상 저널과 별도로 두 트랙의 순서를 유지합니다. 마이크를 스피커로 모니터링하지 않습니다.
- 장치 실패·타임스탬프 오류는 녹화를 실패 상태로 전환하며, 확정된 파일은 보존합니다. 패킷 누락·무음 채움·중복 제거·discontinuity를 계수합니다. 개발 진단을 켠 경우 QPC와 장치 프레임 위치도 별도 기록합니다.

현재 WASAPI 작업 스레드가 디스크 쓰기도 수행합니다. 수집과 쓰기를 제한된 큐로 분리하고, 디스크 지연·장치 손실·30분 녹화 시험을 수행해야 합니다. 원본을 조용히 건너뛰거나 입력 장치를 자동 변경하여 실패를 숨기지 않습니다.

## 프로젝트·편집·출력

프로젝트 스키마 v3에 선택한 트랙, 볼륨·음소거, 부분 복구 표시를 추가했습니다. v1/v2 파일은 원본 백업을 남긴 뒤 이행합니다. WAV 프로필·길이와 전체 SHA-256을 확인하고, 복사 후 최종 manifest를 원자적으로 확정합니다. 중단된 복사는 재시도할 수 있으며 기존 사본을 다른 내용으로 덮어쓰지 않습니다.

복구 시 영상과 모든 선택된 원본 오디오의 공통 구간만 편집 범위에 남깁니다. 샘플 구간을 먼저 병합한 뒤 마이크로초 경계를 안쪽으로 반올림하여, 존재하지 않는 끝 샘플이나 인접 파일 사이의 가짜 빈 구간을 만들지 않습니다. 1~12샘플의 짧은 끝 구간과 소수 마이크로초 경계 복구를 별도 회귀 검사로 추가했습니다. 트랙을 음소거해도 손상된 원본을 정상으로 간주하지 않습니다. 부분 복구는 프로젝트에 기록하고 UI에도 표시합니다.

`AudioMixer`는 불변 편집 구간·트랙 설정과 검증된 읽기 잠금을 유지합니다. 메모리는 트랙당 최대 5초 캐시로 제한합니다. 미리보기와 내보내기가 같은 출력 샘플 위치를 요청하며, 여러 구간을 삭제한 뒤에도 하나의 48 kHz 격자를 유지합니다. 삭제 구간을 가로질러 보간하지 않습니다. 볼륨·음소거는 편집 revision과 실행 취소/다시 실행에 포함됩니다.

두 트랙의 합은 PCM16 범위에서 포화 처리하고, 잘린 샘플 수를 출력 결과에 남깁니다. 앱은 클리핑이 있으면 볼륨을 낮추고 다시 저장하도록 안내합니다. 이 처리는 자동 음량 조정이나 고품질 리미터가 아닙니다.

MP4 내보내기는 H.264 영상과 AAC-LC 48 kHz 스테레오 192 kbps 오디오를 같은 시간 순서로 제출합니다. 임시 파일을 전체 디코딩하고 영상·음성 길이를 확인한 뒤 새 목적지에 확정합니다. 취소·콜백 오류·기존 목적지 충돌은 원본과 기존 파일을 보존합니다. 모든 트랙을 명시적으로 음소거하면 오디오 스트림 없는 MP4가 됩니다. AAC의 1024샘플 블록 패딩은 별도 길이·신호 검사로 확인합니다. [Microsoft AAC encoder 문서](https://learn.microsoft.com/en-us/windows/win32/medfound/aac-encoder), [MP4 sink 문서](https://learn.microsoft.com/en-us/windows/win32/medfound/mpeg-4-file-sink).

편집기에서는 `MediaStreamSource`가 같은 PCM 믹서를 읽고, MediaPlayer의 오디오 재생 시계로 표시할 영상 프레임을 선택합니다. 재생 요청마다 플레이어를 분리하여 이전 재생의 지연된 종료·오류 알림이 새 재생을 중단하지 않게 합니다. [Microsoft MediaStreamSource 문서](https://learn.microsoft.com/en-us/uwp/api/windows.media.core.mediastreamsource), [시작 위치 API](https://learn.microsoft.com/en-us/uwp/api/windows.media.core.mediastreamsourcestartingrequest).

통제된 AAC 표본의 편집 경계에서 참조 PCM 대비 측정 지연은 0샘플, 정렬 후 RMSE는 약 0.000556입니다. 3초 출력의 디코딩 오디오 끝은 약 3.008초입니다. 이 값은 오프라인 인코더 검사이며 실제 입력 장치의 A/V 지연 또는 UI의 화면·스피커 정합 실측값이 아닙니다.

Windows 재생 검사는 앱의 `AudioPreviewSource.cs`를 직접 링크해 사용합니다. 테스트의 장치 출력 볼륨을 0으로 설정했으므로 실제 스피커에서 들리는 음질을 확인했다고 주장하지 않습니다. 실제 WinUI 화면 확인 범위도 검증 JSON에 별도로 기록합니다. 볼륨 직접 입력 후 적용에서 이전 값이 저장되는 결함을 실제로 재현했습니다. NumberBox의 Text도 확정 전에는 이전 값이므로, 현재 고정한 WinUI 템플릿의 InputBox와 해당 컨트롤의 지역별 숫자 해석기를 사용합니다. 템플릿 변경으로 입력을 찾지 못하면 이전 값을 저장하지 않고 편집을 거부합니다. SDK를 변경할 때 이 실제 UI 회귀가 필요합니다. [Microsoft NumberBox 구현](https://github.com/microsoft/microsoft-ui-xaml/blob/main/controls/dev/NumberBox/NumberBox.cpp).

수정 후 `app-x64-build-6399-3542`에서 시스템 볼륨 25%를 50%로 입력하고 Enter 없이 적용해, 화면과 저장된 프로젝트 모두 50%를 유지하는 것을 확인했습니다. 마이크를 음소거한 상태에서 실제 폴더 선택기로 MP4를 저장하고 앱을 종료·재실행해 설정 유지를 확인했습니다. 출력은 1920×1080 30fps 90프레임 전체 디코딩, AAC 48 kHz 스테레오, 연속 타임스탬프, 채널별 마이크 음소거와 시스템 50% 신호 검사를 통과했습니다. 재생은 오류 표시 없이 끝 부근에서 정지 상태로 돌아왔으며, 정확한 마지막 프레임이나 실제 스피커와 화면의 정합 실측은 포함하지 않습니다.

기능 회귀 86개를 실행한 뒤 마지막 WinUI 빌드에는 숫자 입력 처리만 수정했습니다. 같은 네이티브 DLL을 사용하며, 앱과 테스트 harness의 관리 어셈블리 해시는 빌드별로 분리해 보존합니다. 실제 UI 검사는 이 마지막 앱 빌드에서 수행했습니다. 다른 로캘·키보드만 사용하는 조작·다른 숫자 편집란은 아직 검증하지 않았습니다.

## 남아 있는 출시 차단 결함

최신 `run-4609-11655/audio-capture`는 기능 테스트를 통과했지만 기대 주파수 성분 검사에서 **FAIL**입니다. 이 표본의 최대 무음은 25.27ms로 짧은 50ms 검사는 통과했습니다. 앞선 `run-344-31709/audio-capture`에서는 440 Hz 성분 비율이 약 0.258~0.348이었고, 최대 무음이 **128.75ms**였습니다. 앞선 실패는 그대로 보존하며 원인이 해결됐다고 판정하지 않습니다. 일시정지 중 톤 제외와 파일 길이 일치는 음질 통과를 대신하지 않습니다.

이전 표본에서 장치 프레임 시계와 패킷 QPC의 상대 차이가 관찰됐습니다. 테스트 톤 생성, VM 장치 시계, 캡처·보간·쓰기의 영향을 아직 분리하지 못했습니다. 생성기에 제출한 PCM 파일은 실제 장치에서 끊김 없이 재생됐다는 증거가 아닙니다. 다음 실험에서는 톤 생성기의 버퍼 underrun과 실제 장치 출력 기준을 함께 계측해야 합니다.

최신 후보의 일반 캡처는 최대 400ms 반복 프레임과 기준 테스트 창의 385.87ms 정지로 품질 FAIL입니다. 대상 종료 표본도 반복 프레임 때문에 FAIL이며, 강제 종료·크기 변경·오디오 캡처 표본의 영상 검사는 통과했습니다. 앞선 후보에서는 강제 종료 표본도 실패했습니다. 결과를 실행별로 기록하며, 전체 디코딩·색상이 유효해도 출시 성능을 인증하지 않습니다.

마이크 실제 녹음, 두 장치 동시 녹음, 장치 분리·권한 거부, 장시간 드리프트, 가림 중 오디오 제외의 실제 발표 UI 검사, H1~H4에서의 A/V 절대 오차 ≤50ms, 청취 평가가 남았습니다. 영역 선택·접근성·공유 서비스·서명 배포·베타와 독립 검토도 기존 범위대로 계속 필요합니다.

## 재실행

- `scripts/Verify-Modes.cmd`: 네이티브 → 코어 → 실제 캡처·복구 → 렌더 → 오디오 재생 → 발표 → WinUI publish.
- `scripts/Verify-AudioUX.cmd`: 이미 빌드한 엔진·렌더 표본을 사용해 실제 재생 검사 후 WinUI publish.
- `scripts/Launch-Audio-Review.cmd`: 재생·빌드 통과 후 합성 PCM/실제 WGC 영상 테스트 프로젝트를 새 GUID 폴더에 복사하고 앱을 엽니다. 기존 프로젝트는 덮어쓰지 않습니다.
- `.tools/media-venv/bin/python scripts/Inspect-Audio.py <capture> --fixture-tones`: 실제 톤 녹음의 길이·주파수·무음·일시정지 구간 검사.
- `.tools/media-venv/bin/python scripts/Inspect-AudioExport.py <render-run>`: 통제된 렌더 표본의 독립 A/V 및 신호 검사.

CI에는 빌드·코어·검사기 회귀와 재생 harness 컴파일을 추가했습니다. 원격 CI 실행과 실제 장치 검증은 아직 수행하지 않았습니다.
