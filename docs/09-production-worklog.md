## 이전 오디오 후보

이전 오디오 후보는 오디오 수집과 파일 쓰기를 제한된 큐로 분리했습니다. 큐 포화·쓰기 오류에서 장애 전 확정 파일 보존, 복구 표시 수정과 동일 빌드의 89개 기능 회귀는 [저장 분리 기록](12-audio-storage-queue.md)에 보존합니다. 시계 오차와 일부 영상 연속성 실패는 계속 유지합니다.

후속 시계 수정 후보에서는 원시 PCM·재생 장치 시계·보간 결과를 분리해 음정 변화의 직접 원인을 확인했습니다. 연속 시계 보정 후 남은 무음·시계 잔여 오차와 최신 전체 회귀는 [오디오 시계 수정 기록](11-audio-clock-investigation.md)에 보존합니다. 아래는 앞선 오디오 기능 후보 기록입니다.

두 트랙 원본·공통 일시정지 시간축·복구를 구현하고, 동일 편집 구간을 사용하는 PCM 믹서·AAC 내보내기·실제 MediaPlayer 재생까지 연결했습니다. Windows 기능 검사와 독립 출력 검사는 통과했지만 실제 녹음의 음질·무음 검사에는 실패가 남아 있습니다. 구현 경계, 정확한 테스트 수, 다음 원인 분리 실험은 [오디오 기록](10-audio-pipeline.md), 실행별 해시는 [검증 JSON](validation/windows-audio-foundation-2026-09-12.json)에 기록합니다.

## 캡처 계측과 개선

기존 `RecordingSink`는 GPU 읽기·인코딩·5초 세그먼트 마감을 순서대로 수행했습니다. 파일 마감이 원인일 가능성을 먼저 검토했지만, 계측 표본에서는 GPU 읽기 최대 412.196ms, 파일 마감·flush 최대 16.625ms로 나타났습니다. 원인을 구분할 수 있도록 읽기·인코딩·마감·생성·소스 나이의 고정 크기 히스토그램과 개발용 프레임 타이밍 기록을 추가했습니다. 히스토그램의 p95/p99는 구간 상한이며 정밀 백분위수로 표시하지 않습니다.

GPU 읽기에서는 소비자별 staging 텍스처와 CPU 버퍼를 재사용하고 첫 자원 준비를 녹화 준비 완료 전에 수행합니다. GPU가 사용 중인 자원은 `Map(DO_NOT_WAIT)`로 확인하고 잠시 뒤 다시 확인하여 대기 중 종료 요청을 받을 수 있게 했습니다. 이 플래그는 GPU가 자원을 사용 중일 때 `DXGI_ERROR_WAS_STILL_DRAWING`을 반환합니다. [Microsoft Map 문서](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-map).

WGC 원본을 복사하는 텍스처는 세션당 최대 4개를 재사용합니다. 게시된 스냅샷·녹화·발표 소비자가 참조 중인 텍스처는 재사용하지 않습니다. 사용 가능한 버퍼가 없으면 별도 누락 카운터를 증가시키며, 크기 변경 시 풀을 다시 구성합니다. 합쳐진 도착 알림에서 대기 중 프레임은 제한된 횟수만큼 읽어 최신 프레임을 선택합니다. WGC 프레임을 반환한 뒤 빌린 Surface를 보관하지 않는 원칙도 유지합니다. [Microsoft 캡처 프레임 수명 문서](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).

새 짧은 표본 `run-17186-7763`에서는 353개 출력 프레임 동안 텍스처 3개를 할당했고 버퍼 부족 누락은 0개였습니다. 다만 스케줄러의 누락은 8개이고 같은 프레임 반복은 최대 300ms였으므로 성능 PASS가 아닙니다.

## 검사 자체에서 발견한 문제

이전 독립 검사는 각 세그먼트의 첫 프레임에서만 색상을 확인했습니다. 보존된 실패 파일의 119개 프레임을 전부 확인하자 0·91·92번째 프레임에서 색상 패치가 비어 있었습니다. 검사를 모든 프레임으로 확장하고, 파일 내부뿐 아니라 세그먼트 경계의 시간 간격도 확인합니다.

테스트 창은 배경을 지운 뒤 텍스트·색상 패치를 직접 그려 중간 상태가 WGC에 잡힐 수 있었습니다. 완성된 메모리 비트맵을 한 번에 복사하도록 수정했습니다. [Microsoft 메모리 DC 문서](https://learn.microsoft.com/en-us/windows/win32/gdi/memory-device-contexts). 원본 프레임을 검사에서 제거하거나 앱에서 빈 화면을 감추는 필터는 추가하지 않았습니다.

수정한 테스트 창에는 32비트 프레임 번호와 체크섬을 넣고 그리기 완료 QPC를 기록합니다. 새 표본에서는 모든 프레임의 색상·프레임 번호가 유효했지만, 원본 그리기도 최대 347.928ms 멈췄습니다. 따라서 이 VM 표본만으로 300ms 반복을 앱에서 만든 정지로 단정하지 않습니다. 동적 기준 소스 자체가 멈춘 표본은 출시 성능 인증에 사용할 수 없습니다.

검사기의 회귀 시험 9개는 실제 H.264 표본으로 정상 다중 세그먼트, 중간의 빈 프레임, 세그먼트 사이 333ms 간격, 파일 경계를 가로지르는 프레임 반복, 역행하는 프레임 번호, 테스트 창의 정지, 디코딩 개수 불일치를 구분합니다. 변조 체크섬 거부도 검사합니다. macOS에서 9/9 통과했으며, 합성 미디어를 사용하는 검사기 시험은 실제 캡처 시험을 대신하지 않습니다. CI 실행 정의와 로그 보존을 추가했지만 원격 CI는 아직 실행하지 않았습니다.

## 실행과 증거

- Windows: `scripts/Verify-Modes.cmd`로 네이티브·코어·녹화 복구·렌더·발표·WinUI 빌드를 검사합니다.
- 짧은 계측 표본: `scripts/Verify-Native.cmd`. 원본·바이너리 해시·`capture-performance.json`·개발용 타이밍을 실행별 폴더에 보존합니다.
- 독립 검사: `.tools/media-venv/bin/python scripts/Inspect-Media.py <capture-directory> --fixture`. `--output`으로 이전 보고서를 보존하면서 추가 감사를 기록할 수 있습니다.
- 검사기 회귀: `.tools/media-venv/bin/python tests/media/test_inspect_media.py`.

정확한 실행별 수치·해시와 전체 회귀 결과는 [검증 JSON](validation/windows-capture-readiness-2026-09-12.json)에 연결했습니다. 기존 캡처 품질 FAIL과 출시 게이트 미통과 상태는 유지합니다. 오디오의 후속 구현·검증은 위 새 기록에서 계속하며, 영역 선택과 장치·장애 처리도 남아 있습니다. 동적 기준 소스와 실제 장비를 확보하는 성능 검증도 계속 필요합니다.
