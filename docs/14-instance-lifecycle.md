# 중복 실행·창 복원·종료 안정성

## 사용자에게 달라진 동작

Glide를 다시 실행하면 현재 작업 창으로 돌아옵니다. 최소화 상태와 녹화 중에도 기존 프로세스·프로젝트를 유지합니다. 같은 사용자 프로필을 두 프로세스가 동시에 열어 복구·저장·단축키 등록을 수행하지 않도록, 창 생성보다 먼저 소유권을 확보합니다. 창을 닫은 뒤 UI 종료까지 소유권을 유지하며, 새 실행은 기존 앱이 종료 중이면 안내 후 끝납니다.

사용자 SID와 정규화한 프로필 경로로 Windows mutex와 활성화 pipe를 구분합니다. mutex는 사용자 범위로 제한하고 로그인 세션을 가로질러 같은 프로필의 동시 소유를 막습니다. 활성화 요청은 같은 로그인 세션에서만 처리합니다. pipe에는 한 바이트 활성화 요청만 전달하며 파일 경로·URI·명령 실행은 지원하지 않습니다. 소유권이 있던 프로세스가 비정상 종료하면 Windows가 해제한 mutex를 다음 실행이 인계합니다. [.NET 이름 있는 동기화 범위](https://learn.microsoft.com/en-us/dotnet/api/system.threading.namedwaithandleoptions?view=net-10.0)

pipe는 현재 사용자로 제한하며 요청·연결 시간에 상한을 둡니다. Windows에서 `CurrentUserOnly`에는 권한 상승 수준 검사도 포함됩니다. 다른 계정·다른 로그인 세션·권한 상승 조합은 이번 VM에서 실제 시험하지 않았습니다. [PipeOptions 공식 문서](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions?view=net-10.0)

## 실제 실패에서 수정한 부분

- 8개 프로세스를 동시에 시작했을 때 기존 창 활성화는 7번 수신했지만, 연결을 즉시 끊어 6개 요청자가 응답을 읽지 못했습니다. 응답 수신 확인을 기다리되 동일한 시간 제한을 적용했습니다. Windows의 pipe 연결 해제는 읽지 않은 데이터를 버립니다. [DisconnectNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe)
- 잘못된 클라이언트가 먼저 연결을 끊으면 `IsConnected`가 false가 되어 다음 연결을 준비하지 못했습니다. 실제 수락 여부를 별도로 추적해 pipe를 초기화합니다.
- 홈에서는 창이 복원됐지만 녹화 중에는 PowerShell 뒤에 남았습니다. 요청자가 Windows에서 확인한 기존 프로세스 ID에 활성화 권한을 넘기고, 기존 창은 복원 후 `SetForegroundWindow`를 호출합니다. Windows가 거절하면 작업 표시줄 알림을 사용합니다. [AllowSetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow)
- 개발 진단 로그의 재개 버튼이 최초 문구인 ‘녹화 일시정지’로 기록되던 문제를 수정했습니다. 클릭 당시 문구를 기록합니다.
- 테스트 실행 환경이 없어서 프로세스가 음수 코드로 종료됐는데도 CMD의 `if errorlevel 1` 검사를 통과하는 문제를 확인했습니다. 0이 아닌 종료 코드를 실패로 처리하며, 렌더 준비 분기는 괄호 블록의 조기 변수 확장을 피합니다. Robocopy의 0~7 성공 규칙은 유지합니다.

수정 전 동시 실행 실패 2회, 런타임 누락, 실제 녹화 중 창 활성화 실패와 원본 영상은 보존했습니다. 후속 통과 결과로 이전 실패를 덮어쓰지 않습니다.
