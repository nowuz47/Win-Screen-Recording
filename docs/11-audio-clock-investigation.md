# 오디오 음정·시계 원인 분리

2026-09-12 · 개발 진행 중 · **NOT READY**

아래는 시계 수정 후보의 기록입니다. 후속 수집·저장 큐 분리와 최신 장애·성능 실측은 [저장 분리 기록](12-audio-storage-queue.md)에 이어집니다.

이 문서는 [오디오 기능 구현 후보](10-audio-pipeline.md) 다음의 수정 기록입니다. 이전 기능·실제 UI 검증은 해당 후보의 증거로 보존합니다. 새 후보의 기능 테스트, 실제 음질, 타임스탬프 오차는 각각 판정합니다.

## 확인한 결함과 수정

이전 구현은 연속 WASAPI 패킷의 QPC 간격에 맞춰 패킷 전체를 보간했습니다. `run-8995-28845`에서 보간 전 PCM의 440 Hz를 확인했지만 저장된 WAV는 약 449~450.5 Hz로 이동했습니다. 첫 활성 구간의 장치 샘플 위치는 QPC 대비 약 2.3% 빠르게 진행했습니다. 이 시계 차이를 패킷마다 그대로 오디오 속도에 반영한 것이 저장된 음정 변화의 직접 원인입니다. VM·드라이버 시계가 왜 이렇게 달라지는지는 아직 확정하지 않았습니다.

`AudioPacketClock`은 연속 샘플 위치를 바탕으로 시간축을 유지하고, QPC와의 차이를 2초의 보정 시간 상수로 서서히 반영합니다. 속도 보정은 ±1000 ppm으로 제한하며 패킷별 큰 음정 변화를 막습니다. 위치 불연속과 명시적인 discontinuity는 새 시계 구간으로 분리합니다. 시작·일시정지·재개·종료는 기존 공통 타임라인의 활성 구간과 교차시킵니다.

큰 시계 오류를 해결한 것으로 간주하지 않습니다. 최대 잔여 오차와 보정 제한에 도달한 패킷 수를 `audio-performance.json` v2에 남깁니다. 독립 PCM 검사에 **보고된 QPC 대비 최대 잔여 오차 ≤50ms**를 추가했습니다. 이 검사는 실제 화면과 스피커의 절대 지연 측정을 대신하지 않습니다. 보정 제한으로 음정을 유지하더라도 큰 시계 오류가 남으면 전체 품질은 FAIL입니다.

[WASAPI GetBuffer](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)는 패킷의 첫 샘플 위치와 100ns 단위 QPC를 제공합니다. [IAudioClock.GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)의 위치는 `GetFrequency`와 함께 해석합니다. 원시 카운터 단위를 혼용하지 않고 두 API의 값을 별도로 기록했습니다.

## 원인 분리를 위한 계측

명시적으로 `GLIDE_AUDIO_TRACE_PCM=1`을 설정한 시험만 선택된 트랙의 보간 전 PCM을 기록합니다. WASAPI 소유 버퍼를 반환한 뒤 메모리로 수집하고, 장치별 최대 20초·6000패킷으로 제한합니다. 파일 쓰기는 오디오 클라이언트가 멈춘 후 수행합니다. 생략한 패킷이 있으면 불완전한 진단으로 판정합니다. 일반 앱 실행의 진단 옵션만으로 이 추가 PCM 기록을 켜지 않습니다.

테스트 톤 생성기는 제출 PCM, 장치 시계, 제출 프레임 수, 버퍼 잔량, 호출 간격과 주파수 변경을 기록합니다. 버퍼 잔량 0 관측은 고갈의 증거지만, 0을 보지 못했다고 실제 출력이 연속임을 인증하지 않습니다. 기존 Sleep 폴링에서 151~210ms 호출 간격과 빈 버퍼가 관측돼 이벤트 기반 공급과 MMCSS Audio 작업 등록을 추가했습니다. [Microsoft 이벤트 기반 렌더 예제](https://learn.microsoft.com/en-us/windows/win32/coreaudio/rendersharedeventdriven), [MMCSS 등록 API](https://learn.microsoft.com/en-us/windows/win32/api/avrt/nf-avrt-avsetmmthreadcharacteristicsw).

## 수정 중 보존한 실측

| 후보 | 고정 주파수 성분의 최소 비율 | 최대 무음 | QPC 대비 최대 잔여 오차 | 판정 |
| --- | --- | --- | --- | --- |
| 계측만 추가, `run-8995-28845` | 0.0433 | 49.31ms | 새 지표 없음 | 음정 FAIL |
| 연속 시계 보정, 기존 톤 폴링, `run-10190-30602` | 0.9929 | 112.17ms | 66.85ms | 무음·시계 FAIL |
| 연속 시계 + 이벤트/MMCSS 톤, `run-10823-18641/audio-capture` | 0.9931 | 74.58ms | 86.80ms | 무음·시계 FAIL |

수정 전후 파일·네이티브 해시·원시 패킷·검사 결과를 실행별 폴더에 보존했습니다. 수치는 다른 실행의 최고값을 합쳐 PASS로 만들지 않습니다. 위 성분 비율은 기존 고정된 주파수·시간 구간·80% 기준 그대로 계산했으며, 측정 피크에 맞춰 검사 주파수를 변경하지 않았습니다.

최신 후보는 Windows 코어 58/58, 실제 캡처·복구 6/6, 렌더 13/13, 오디오 재생 5/5, 발표 4/4를 통과했습니다. 독립 AAC 38개와 영상 렌더 비교 11개도 통과했습니다. 같은 엔진의 WinUI publish는 `app-x64-build-30639-10644`이며, 이 후보에서 실제 UI 편집을 다시 수행한 것은 아닙니다. 이전 후보의 UI 검사 범위는 자동 승계하지 않습니다.

최신 톤 생성기는 MMCSS 등록 성공, 이벤트 timeout 0회, 버퍼 0 관측 0회였지만 최대 호출 간격은 158.35ms였습니다. 첫 구간의 렌더 장치 시계도 QPC보다 약 2.7% 빠르게 진행했습니다. 따라서 캡처만의 잘못된 시계라고 단정할 수 없습니다. 원시 패킷에서 독립 계산한 최대 보정 잔여 오차 86.8023ms는 엔진 지표와 일치합니다. 실제 스피커가 연속 재생됐거나 VM 시계 오류가 해결됐다고 판정하지 않습니다.

같은 후보의 영상은 일반·대상 종료·크기 변경 표본의 짧은 검사를 통과했습니다. 강제 종료 표본은 기준 창의 최대 286.02ms 정지 때문에 실패했고, 오디오 캡처 표본은 최대 300ms 반복 프레임과 기준 창의 250.20ms 정지 때문에 실패했습니다. 모든 MP4 세그먼트는 전체 디코딩과 색상 검사를 통과했지만 출시 성능 판정은 FAIL입니다. 실제 실행·소스·바이너리 해시와 결과는 [시계 수정 검증 JSON](validation/windows-audio-clock-2026-09-12.json)에 보존합니다.

## 회귀 검사와 재실행

- 네이티브 시계 검사: 정확한 샘플 시계, 100 ppm 드리프트 수렴, 교대 타임스탬프 흔들림, 과도한 드리프트의 명시적 잔여 오차, 장치 리셋·역행 거부. 기존 일시정지·구간 보간 검사도 유지합니다.
- 독립 PCM 검사기 5개: 정상, 일시정지 소리 유입, 검사 구간 밖 무음, 잘린 WAV, 정상 음정으로 가려진 50ms 초과 시계 오차를 구분합니다.
- `scripts/Verify-AudioClock.cmd`: 진단을 명시적으로 켠 전체 Windows 기능 회귀와 앱 publish.
- `scripts/Verify-Audio.cmd`: 네이티브 빌드와 짧은 실제 시스템 녹음.
- `.tools/media-venv/bin/python scripts/Inspect-Audio.py <capture> --fixture-tones`: 고정된 음질·길이·무음·시계 잔여 오차 검사.
- `.tools/media-venv/bin/python scripts/Inspect-AudioClock.py <capture>`: 보간 전·후 스펙트럼, 재생·캡처 시계와 원시 패킷의 독립 잔여 오차 분석. 품질 기준을 대체하지 않습니다.

## 남은 작업

수집·디스크 쓰기의 제한된 큐 분리, 장치 타임스탬프 안정성 확인, 시계 불확실성의 사용자 안내와 보존 정책, 실제 마이크·두 장치·장시간·실기기 A/V 검증이 필요합니다. MMCSS는 현재 테스트 톤 생성기에 적용했으며 캡처 작업 스레드에 적용했다고 주장하지 않습니다. 캡처 프레임 끊김, 영역·접근성·공유·서명 배포·베타·독립 출시 검토도 계속 남아 있습니다.
