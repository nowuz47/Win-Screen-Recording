## 편집·합성·내보내기 구현

[렌더 통합 검사 7/7](validation/windows-render-2026-09-11.json)은 실제 녹화한 테스트 창의 MP4를 입력으로 사용합니다. 3초 편집의 90프레임, 60fps의 짧은 마지막 프레임, 확대·커서 표시, 렌더 도중 취소, 기존 출력 보호, 원본 쓰기 거부, 콜백 예외 격리, 잘못된 영상과 누락 구간 거부를 확인했습니다. 커서 위치는 비교 가능한 통제 데이터이며 실제 클릭 수집 정밀도를 인증하지 않습니다.

첫 시도에서 테스트 구간이 원본 세그먼트 사이의 9µs 간격을 가로질러 거부됐습니다. 실제 편집 타임라인처럼 존재하는 원본 구간을 유지하도록 테스트를 수정했습니다. 또 디코더의 정렬된 프레임 크기를 표시 크기로 가정해 실패했습니다. 현재는 [표시 영역](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-mt-minimum-display-aperture-attribute)과 [실제 행 간격](https://learn.microsoft.com/en-us/windows/win32/api/mfobjects/nf-mfobjects-imf2dbuffer-lock2d)을 분리하고 NV12의 Y·UV 평면을 유효 영역만 복사합니다. 초기 실패 결과는 `.artifacts/windows-render/run-5033-12508` 및 후속 후보 폴더에 보존했습니다.

별도 PyAV/FFmpeg 디코더로 30/60fps 타임스탬프와 BT.709 태그를 확인했습니다. 4개 표본 프레임에서 미리보기와 인코딩 후 영상의 평균 채널 오차는 약 0.89~1.42/255, PSNR은 약 38.45~39.88dB였습니다. 독립적으로 원본 시각을 선택하고 잘라내기·배치 좌표를 계산한 비교도 통과했습니다. 이는 짧은 회귀 검사이며 G04의 전수 시간·좌표 정밀도 검증을 대체하지 않습니다.

[실제 WinUI 편집 시험](validation/windows-editor-ui-2026-09-11.json)에서는 기존 테스트 녹화의 1~4초만 남기고 수동 확대를 적용했습니다. 실행 취소·다시 실행 후 1920×1080, 30fps, 3초, 90프레임 MP4를 저장하고 앱에서 끝까지 재생했습니다. 앱 종료·재실행 후에도 3초 편집과 확대 1개가 유지됐습니다. 원본 8개 파일의 해시는 편집 전과 모두 같습니다. 이 시험의 확대는 커서가 녹화 대상 밖에 있어 중앙을 사용했습니다.

편집 저장은 디스크 저장 성공 후에만 이력을 확정합니다. 내보내기는 원본 해시를 다시 확인하고 읽기 잠금을 유지하며 임시 MP4를 전체 디코딩·프레임 수·길이 검증한 뒤 새 파일명으로 확정합니다. 취소나 실패는 기존 출력과 원본을 보존합니다. 현재 배경과 화살표 스타일은 고정이며 실제 커서 모양 재현, 실시간 GPU 편집 미리보기, 저장 위치 선택, 강제 종료 후 임시 내보내기 정리와 성능·장시간 검증은 남아 있습니다.

앱의 저장 취소 버튼도 실제로 조작했습니다. 취소한 프로젝트의 출력 폴더에 완성·임시 MP4가 남지 않았고 원본 해시는 유지됐습니다. 짧은 프로젝트에서 긴 프로젝트로 전환할 때 선택 끝값이 이전 길이로 제한되는 UI 버그를 발견해 값보다 허용 범위를 먼저 갱신하도록 수정했습니다.

[최종 UI 회귀](validation/windows-editor-ui-2026-09-11-r2.json)에서 3초 → 약 33.2초 프로젝트 전환의 끝값을 확인했습니다. 녹화 중 앱을 닫는 경우에는 저장이 끝날 때까지 종료를 기다리고 닫는 도중 편집기를 새로 열지 않도록 보완했습니다. 실제로 약 35.6초, 909프레임을 저장한 뒤 앱이 닫혔고 재실행 후 해당 녹화를 편집기에서 열었습니다. 독립 디코더·원본 해시 검사도 통과했습니다. 캡처 프레임률의 기존 성능 제한은 남아 있습니다.

공통 인코더 수정 후 같은 네이티브 DLL로 [녹화·복구 회귀 5/5](validation/windows-integration-2026-09-11-r3.json)도 다시 통과했습니다. 정상·강제 종료·대상 종료·리사이즈의 확정 파일은 독립 디코더 검사도 통과했습니다. [초기 렌더 후보의 실패 기록](validation/windows-render-failures-2026-09-11.json)도 별도로 보존했습니다.

Parallels CLI의 VM 실행·게스트 명령 기능은 설치된 에디션에서 제한되어 있어 GUI로 진행합니다. CUA 입력 연결과 잠금 해제 후 위 Windows 검증을 재개했습니다. GPU 캡처 시작 시 게임용 상대 마우스 모드가 자동 활성화되어 포인터가 어긋나는 문제는 Parallels의 Mouse 설정을 `Auto-detect for games`에서 `Don’t optimize for games`로 변경해 해소했습니다. 이후 실제 버튼 클릭 로그로 입력 도달을 확인했습니다. 사용자 요청으로 개발 중 임시 `caffeinate` 절전 방지와 5분 간격 상태 확인 자동화를 활성화했습니다. Windows 스크립트 실행 정책과 잠금 암호 정책은 변경하지 않았습니다.

## 실행 방법

코어 테스트는 SDK 10.0.401이 있는 환경에서 다음과 같이 실행합니다.

```sh
dotnet run --project tests/Glide.Core.Tests -c Release -- all
```

현재 Parallels 작업 환경에서는 Windows PowerShell에서 다음 스크립트를 실행합니다. 일반 PC용 설치 파일이 아니라 개발 도구가 있는 이 VM의 검증 스크립트입니다.

```powershell
& '\\Mac\Home\Desktop\AI Slops\Win-Screen-Recording\scripts\Verify-Windows.cmd'
```

이 스크립트는 코어 테스트 → 네이티브 빌드 → WinUI publish → 네이티브 빌드 성공 시 실제 12초 캡처 probe와 Windows 통합 검사를 실행합니다. Probe는 자신이 만든 움직이는 테스트 창만 녹화하고, 생성된 모든 MP4를 디코딩해 인코딩 프레임 수와 비교합니다. 성공하더라도 영상의 시각적 내용·커서 정합·음성·GPU 성능은 추가 검증해야 합니다.

SDK와 빌드 결과는 Windows `%LOCALAPPDATA%\GlideDev` 아래에 두며 시스템 PATH를 바꾸지 않습니다. 원시 로그와 테스트 파일은 저장소 `.artifacts` 아래에 복사합니다. Native 실행마다 별도 폴더를 사용합니다. WinUI도 실행 중인 빌드를 덮어쓰지 않도록 `app-x64-build-*`에 publish하고, 성공한 경로만 `app-current.txt`에 기록합니다. 앱 시작은 `scripts/Launch-App.cmd`를 사용합니다.

수정 후보의 네이티브 빌드·짧은 녹화는 `scripts/Verify-Native.cmd`, 실제 복구·가져오기 통합 검사는 그 후 `scripts/Test-Windows-Integration.cmd`로 실행합니다. `scripts/Verify-Recovery.cmd`는 네이티브 빌드와 5개 통합 검사를 함께 수행합니다. 통합 검사의 강제 종료는 테스트 자체가 생성한 녹화 프로세스만 대상으로 합니다. 성공하더라도 한 VM의 소수 시험이며 G03의 60회·장비별 표본을 대체하지 않습니다.

별도 디코더 회귀 검사는 테스트용 Python 환경에 `scripts/requirements-media-tests.txt`를 설치한 뒤 실행합니다.

```sh
python scripts/Inspect-Media.py .artifacts/native-captures/<run-id> --fixture
```

생성된 `media-inspection.json`에는 파일 해시, 디코더 버전, 프레임 수, PTS, 색상 태그와 각 검사 결과가 남습니다. 현재의 초기 캡처에 실행하면 알려진 품질 문제를 검출하고 종료 코드 1을 반환합니다. 테스트 창의 색상 좌표를 사용하는 `--fixture`는 일반 사용자 영상에 적용하지 않습니다.

편집·렌더 검사는 `scripts/Verify-Editor.cmd`로 네이티브 빌드 → 렌더 검사 → Windows 코어 검사 → 앱 publish를 수행합니다. `scripts/Test-Render.cmd`는 자체 테스트 창을 녹화한 캐시를 입력으로 사용하며 결과를 `.artifacts/windows-render/run-*`에 보존합니다. 입력에는 합성 커서 좌표를 적용해 합성 위치를 통제합니다.

```sh
python scripts/Inspect-Render.py .artifacts/windows-render/<run-id>
```

앱에서 녹화를 선택하면 편집 탭을 엽니다. 선택 시작·끝은 현재 편집 타임라인의 초 단위입니다. MP4는 해당 프로젝트의 `exports` 폴더에 저장하며 저장 직후 왼쪽의 저장 폴더 버튼으로 열 수 있습니다.

별도 Windows 개발 환경에서는 CMake와 SDK를 설치한 뒤 다음 순서로 빌드할 수 있습니다.

```powershell
cmake -S . -B build/native -A x64
cmake --build build/native --config Release
dotnet publish src/Glide.App -c Release -r win-x64 -p:Platform=x64 -o out/app
Copy-Item build/native/Release/Glide.Capture.dll out/app/Glide.Capture.dll
```

위 CMake 경로 자체는 아직 실행하지 않았으며 실제 네이티브 빌드는 MSVC 스크립트로 수행했습니다. WinUI 독립 배포 설정은 [Microsoft 배포 문서](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app)를 기준으로 구성했습니다. 정식 서명·설치·업데이트 검증은 별도입니다.

1. 현재 캡처 경로의 프레임 전달·샘플 제외·큐 손실을 구분해 계측하고, 목표 프레임률을 만족하는 수집·변환 경로 구현.
2. 디스크 부족·장치 손실·장시간 녹화 장애 처리, 창 리사이즈 연속 녹화. 강제 종료·대상 종료·리사이즈 중단 보존의 짧은 VM 검사는 통과.
3. Raw Input / 독립 커서 수집, DPI·창 경계·클릭 시간 실측. 현재 프레임별 버튼 폴링은 짧은 클릭을 놓칠 수 있으므로 정식 기준 미충족.
4. CPU 기준 합성·프레임 탐색·MP4 내보내기를 GPU 경로와 실시간 편집 재생으로 확장. 현재 실제 디코딩·기본 편집·내보내기는 구현했지만 성능 인증 대상 구현은 아님.
5. 구현된 WASAPI 두 트랙·일시정지·AAC·재생의 시계 불확실성 안내·보존 정책, 파일 I/O 취소·장치 손실·실제 마이크·동시 두 장치·장시간 검증. 제한된 수집·쓰기 큐와 짧은 장애 주입은 구현·검사했지만 실제 입력의 음질·동기화를 보장하지 않음.
6. 영역·PNG 캡처, 스타일·효과 편집, 공유 서버, 접근 제어, 서명된 설치·업데이트.
7. 기준 장비 H1~H4의 반복·장시간 시험, 최소 14일 베타, 공유 서비스 운영 검증, G00~G11 최종 판정.
