# 오디오 수집·저장 분리와 장애 복구

2026-09-12 · 개발 진행 중 · **NOT READY**

[오디오 시계 수정](11-audio-clock-investigation.md) 다음 후보입니다. 수집 스레드에서 파일 쓰기를 제거하고, 저장 지연·오류를 실제 Windows 캡처와 함께 주입해 확정 원본의 보존을 검사합니다. 기존 음질·시계·영상 연속성 기준은 유지합니다.

## 구현한 동작

WASAPI 클라이언트와 모든 GetBuffer/ReleaseBuffer는 하나의 수집 스레드가 소유합니다. 이 스레드는 선택한 장치의 패킷을 복사해 소유 버퍼를 반환한 뒤 큐로 넘깁니다. MMCSS Audio 작업으로 등록하며 성공·실패를 계측합니다. 장치 변경이나 자동 대체는 하지 않습니다.

다른 스레드가 시간 보정·PCM 변환·WAV 쓰기·flush·저널·진단 파일을 담당합니다. 큐 잠금 안에서는 소유권 이동과 카운터 갱신만 수행합니다. 파일 쓰기나 변환을 큐 잠금 아래에서 실행하지 않습니다.

큐 상한은 **512개 명령과 PCM 비용 768,000바이트**입니다. 48 kHz 스테레오 float를 기준으로 한 트랙 2초, 두 트랙 합계 1초에 해당합니다. 무음 패킷에도 같은 비용을 부여하고, PCM이 없는 제어 명령은 개수 상한으로 제한합니다. 이는 큐의 대기 데이터 상한이며 프로세스 전체 메모리 상한이 아닙니다. 수집 중인 패킷·처리 중인 패킷·보간용 다음 패킷과 명시적 진단 버퍼는 별도입니다.

- 정상 종료: 새 수집을 멈추고 큐를 닫은 뒤, 받은 명령을 순서대로 처리하고 남은 WAV를 확정합니다.
- 큐 포화: 패킷을 조용히 건너뛰지 않고 `ERROR_BUFFER_OVERFLOW`를 보고합니다. 수집은 멈추며 이미 받아 둔 명령은 처리합니다. 오류 뒤에 영상 길이를 맞추려고 새 무음을 덧붙이지 않습니다.
- 쓰기 실패: 첫 오류를 유지하고 큐를 중단합니다. 확정된 WAV·저널은 변경하지 않습니다. 완료하지 못한 WAV는 저널에 추가하지 않고 원본 폴더에 남깁니다. 받아 둔 데이터 중 미처리 명령은 별도로 계수합니다.
- 복구: 확정된 영상과 선택한 오디오의 공통 구간을 사용합니다. 파일 길이가 우연히 정상이어도 녹화·오디오 실패 표식이 있으면 프로젝트의 복구 상태를 저장하고 재개방 때 유지합니다.

계측의 `accepted`는 큐가 받은 명령, `consumed`는 큐에서 꺼낸 명령입니다. `consumed`를 파일 쓰기 완료 수로 해석하지 않습니다. 명령에는 PCM 외에도 무음 경계·일시정지 flush가 포함됩니다. `rejected`, `discarded`, 큐 최고 점유량과 대기 시간, 저장 처리 시간, 장치 버퍼 점유 시간, 수집 호출 간격을 별도로 기록합니다.

## 장애 시험의 증거 경계

전용 probe 모드에서 실제 시스템 소리를 녹음합니다. 첫 5초 WAV가 확정되면 저장 스레드는 체크포인트를 남깁니다. Windows 검사기가 그 파일의 SHA-256을 읽고 확인 파일을 쓴 후에만 장애가 진행됩니다. 이 확인이 1.5초 안에 오지 않으면 시험은 실패하며 성공으로 간주하지 않습니다.

`--audio-writer-stall`은 저장 스레드를 3초 멈춰 실제 큐 포화를 만듭니다. `--audio-write-failure`는 같은 저장 경계에서 쓰기 실패 HRESULT를 주입합니다. 자동 오류 종료, 반복 종료 호출, 저장 파일 전체 디코딩, 큐 상한, 장애 전후 WAV 해시와 복구 프로젝트 재개방을 검사합니다. 물리 디스크를 채우거나 분리한 시험은 아닙니다.

템플릿 큐는 macOS 일반 실행·ThreadSanitizer와 Windows 네이티브 검사에서 소유권 이동, FIFO, 무게·명령 상한, 정상 닫기의 drain, 중단·대기 해제, 10,000개 동시 전송을 검사합니다. ThreadSanitizer 대상은 이 큐 시험이며 전체 WinUI/WASAPI 앱이 아닙니다.

복구 표식 회귀는 수정 전에 `Expected True, got False`로 실패했습니다. 실패 표식을 반영한 뒤 macOS 코어 59/59가 통과했습니다. 코어의 가짜 영상 바이트는 저장·메타데이터 조합만 검사하며, 실제 미디어 판정은 Windows 시험과 독립 디코더를 사용합니다.

## 현재 검증

첫 큐 후보는 Windows 기능 88개를 통과했습니다. 정상 녹음의 최고 큐 점유량은 5개 명령·15,360바이트였고 거부·폐기는 없었습니다. 3초 지연 표본은 768,000바이트 상한에서 1개 명령을 거부하고 이미 받은 819개 명령을 모두 꺼내 처리했습니다. 쓰기 실패 표본은 미처리 명령 9개를 폐기했으며, 장애 전 확정 WAV의 해시는 유지됐습니다.

복구 표식과 추가 지연 계측을 포함한 후속 후보는 macOS·Windows 코어 각각 59/59, Windows 캡처·복구·장애 주입 8/8, 렌더 13/13, 재생 5/5, 발표 4/4를 통과했습니다. Windows 기능 합계는 89개이며, 독립 AAC 38개와 영상 렌더 11개도 통과했습니다. 앱 publish는 `app-x64-build-17581-10414`입니다. 이 후보에서 실제 UI 편집 조작은 다시 수행하지 않았습니다.

`run-15941-18642/audio-capture`의 정상 큐 최고 점유량은 4개 명령·11,520바이트였습니다. 최대 큐 대기 17.28ms, 저장 명령 처리 7.02ms, 수집 호출 간격 22.97ms, 장치 버퍼 점유 0.332ms였으며 거부·폐기는 없었습니다. 이것은 짧은 VM 표본의 최댓값이며 실기기 지연 분포를 인증하지 않습니다.

같은 실행의 3초 저장 지연은 큐의 768,000바이트 상한에서 거부 1개·폐기 0개를 기록했고 받은 820개 명령을 모두 꺼내 처리했습니다. 쓰기 실패는 큐의 미처리 명령 10개를 폐기했습니다. 두 경우 모두 장애 전 확정 WAV의 해시와 재개방 후 복구 표시가 유지됐습니다. 쓰기 실패의 미확정 끝부분은 보존 원본에 남아 있으며, 정상 완료 영상의 길이 일치 기준에는 실패합니다. 복구 프로젝트는 공통으로 확정된 5초를 사용합니다. 이를 정상 녹음의 품질 PASS로 바꾸지 않습니다.

정상 톤 녹음의 최대 무음은 33.06ms로 50ms 검사를 통과했지만, 보고된 장치 QPC 대비 잔여 오차는 **84.6301ms**로 실패했습니다. 원시 패킷에서도 같은 오차를 독립 계산했습니다. 최신 영상의 일반·강제 종료 표본과 저장 장애 표본에는 반복 프레임 또는 기준 창 정지 실패가 남았고, 대상 종료·크기 변경·오디오 정상 캡처 표본은 짧은 검사를 통과했습니다. 원본 세그먼트는 전체 디코딩·색상 검사를 통과했습니다. [후보별 검증 JSON](validation/windows-audio-queue-2026-09-12.json)에 같은 빌드의 통과·실패를 함께 보존합니다.

## 남아 있는 출시 조건

장치 시계의 불확실성과 사용자 안내, 실제 마이크·두 장치·권한·장치 손실, 장시간 녹화·실기기 A/V 측정이 필요합니다. 동기 파일 I/O 자체가 운영체제에서 장시간 멈추는 경우의 취소·종료 시간도 아직 보장하지 않습니다. 큐가 유한하다는 사실만으로 파일 시스템 호출의 종료 시간을 보장할 수 없습니다.

원시 녹음의 시계 잔여 오차와 일부 영상 표본의 반복 프레임·기준 창 정지 실패는 별도로 유지합니다. 영역 선택·접근성·공유·서명 설치·업데이트·베타·독립 출시 검토까지 기존 G00~G11, M01~M11, 모션 기준을 그대로 적용합니다.
