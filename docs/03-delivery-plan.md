# 개발 순서와 검증 기준

2026-09-10 · 일정은 추정이며 구현 착수 전 재산정

이 문서는 기술 검증부터 공개 베타까지의 개발 계획입니다. 정식 출시(GA)는 [Production Ready 기준 v1.0](04-production-readiness.md)의 별도 게이트를 모두 통과해야 합니다. 아래 탐색용 성능 목표와 정식 기준이 다르면 정식 기준을 우선합니다.

## 먼저 확인할 것

2026-09-12 최신 작업은 [Production Ready 개발 기록](09-production-worklog.md)에 있습니다. Windows 잠금은 해제됐으며 실제 검증을 진행 중입니다. 아래의 일정과 잠금 대기 서술은 당시 계획·상태 기록입니다.

2026-09-11 변경: 현재는 두 모드 기반 구현이 추가된 후보입니다. 다음 단계는 새 DLL의 Windows 빌드·기존 회귀·새 발표 검사·WinUI 실제 조작입니다. Mac 잠금으로 검증이 대기 중이며, 결과 확인 전에 후속 장치·오디오·공유 작업을 출시 완료로 처리하지 않습니다. [현재 코드와 남은 작업](06-two-mode-implementation.md), [추가 출시 게이트](07-two-mode-release-gates.md)를 함께 적용합니다. 아래 일정은 기존 탐색 계획입니다.

가장 먼저 만들 결과물은 **30초의 실제 Windows 녹화에서, 원본 커서를 제거하고 기록된 커서를 합성한 뒤 한 번의 자연스러운 자동 확대를 MP4로 내보내는 기술 샘플**입니다.

편집기 전체보다 이 샘플을 먼저 만드는 이유는 커서 동기화, 창 좌표, GPU 경로가 제품의 핵심 품질을 결정하기 때문입니다. 샘플이 실패하면 UI 작업을 확대하기 전에 원인을 해결합니다.

## 단계별 계획

가정: Windows 미디어 경험이 있는 엔지니어 1명, 앱 UI 엔지니어 1명, 부분 참여 디자이너·QA. 세 단계는 순차 기준이며 품질 문제와 범위 변경에 따라 늘어날 수 있습니다. 1인 개발 일정으로 그대로 환산하지 않습니다.

| 단계 | 예상 기간 | 산출물 | 다음 단계로 가는 조건 |
| --- | --- | --- | --- |
| 1. 제품·기술 검증 | 2~3주 | 사용자 과제 관찰, UX 초안, 네이티브 녹화·합성 샘플 | 커서 분리·클릭 동기화·실제 MP4 재생 확인, 스택 결정 |
| 2. 내부 MVP | 추가 6~9주 | 녹화·미리보기·자동 확대·기초 편집·PNG/MP4·프로젝트 복구 | 테스트 사용자가 처음부터 파일 저장까지 완료, 주요 장비에서 품질 기준 통과 |
| 3. 공개 베타 | 추가 3~5주 | 중간 구간 삭제·화면 비율·링크 공유·배포·진단 | 공유 실패·삭제·만료 검증, 설치·업데이트 확인, 출시 차단 문제 해결 |

합계는 약 11~17주의 계획용 범위입니다. 팀 역량·인코더 호환성·클라우드 요구에 따라 변경될 수 있습니다. 외부 약속에 사용하기 전 1단계 결과로 다시 추정해야 합니다.

11~17주는 공개 베타까지의 추정이며 GA까지의 약속이 아닙니다. 베타 이후 최소 14일의 사용자 관찰, 실기기 반복·복구 검증, 서명된 배포물·공유 운영 검증을 수행합니다. 검증은 가능한 범위에서 겹쳐 진행하되 표본과 증거가 모두 확보되기 전에는 정식 출시하지 않습니다. 각 후보의 결과는 [출시 후보 판정표](release-readiness-template.md)에 기록합니다.

## 1단계 기술 샘플의 범위

| 검증 | 실험 | 통과 기준 |
| --- | --- | --- |
| 화면 수집 | 모니터와 일반 앱 창 각 30초 | 원본 재생, 프레임 누락과 크기 변화 관찰 가능 |
| 커서 분리 | 표준 포인터와 텍스트 커서 전환 | 원본에 OS 커서가 없고 위치·모양 재합성 가능 |
| 클릭 동기화 | 시각 반응하는 테스트 버튼을 반복 클릭 | 60fps 기준 클릭 강조와 버튼 반응의 차이 1프레임 이내 목표 |
| 좌표 | 두 모니터, 100%·150% 배율, 창 이동·리사이즈 | 기준점 오차가 정의된 허용 범위 안에 유지 |
| 음성 | 마이크·시스템 소리 동시 녹화 | 분리 트랙 재생, 시작·끝 A/V 오프셋 측정 가능 |
| 확대 | 클릭 2~3개와 긴 이동·드래그 포함 | 클릭 대상 보존, 화면 밖 빈 영역·중복 커서 없음 |
| 합성·인코딩 | 같은 장면을 미리보기와 MP4에서 비교 | 구도·커서 위치·효과 시점 일치 |
| 복구 | 녹화 프로세스 강제 종료 | 마지막 확정 세그먼트까지 복원, 손실 범위 표시 |

실험에서는 색이 바뀌는 버튼과 오디오 비프 등 기준 신호를 가진 별도 테스트 앱을 사용합니다. 눈으로 ‘비슷하다’고 판단하는 것과 좌표·시간 오차를 측정하는 것을 구분합니다.

## 초기 성능 목표

다음은 실측 결과가 아닌 목표입니다. 기준 장비는 PoC 시작 때 CPU·GPU·RAM·SSD·드라이버·OS 빌드까지 고정해 기록합니다. 내장 GPU 노트북 1대와 외장 GPU 데스크톱 1대 이상으로 시작합니다.

| 항목 | 제안 목표 | 측정 조건 |
| --- | --- | --- |
| 기본 영상 | 1080p 60fps, 30fps 대안 | 웹·일반 앱 시연. 4K 캡처는 별도 프로필 |
| 프레임 처리 | 획득 후 합성·제출 p95가 16.7ms 예산 안 | CPU 시간과 GPU 시간을 분리, 인코더 큐 대기 별도 기록 |
| 앱으로 인한 프레임 손실 | 스트레스 시나리오 10분에서 0.5% 미만 | 정지 화면에서 WGC가 새 프레임을 안 주는 경우와 구분 |
| A/V 동기화 | 10분 녹화에서 절대 오차 50ms 이내 | 시작·중간·끝 기준 신호로 측정 |
| 커서 정합 | 클릭 시 원본 좌표계 2px 이내 목표 | DPI·핫스팟 포함. 일반 이동 평활화에는 별도 허용 |
| UI 반응 | 재생 중 일반 조작 p95 100ms 이내 | 효과 변경의 최종 렌더 완료 시간은 별도 측정 |
| 확대 분석 | 5분 프로젝트에서 3초 이내 목표 | 미디어 전체 디코딩 없이 이벤트 기반 분석 |
| 내보내기 | 1080p60에서 영상 길이 이내 완료 목표 | 기준 GPU에서 기본 효과 적용. 장치 전체에 보장하지 않음 |
| 장시간 안정성 | 30분 녹화 후 정상 종료·재열기 | 무제한 메모리 증가 없음, 기준 장비의 사용량 수치 보고 |

60fps 자체를 제품 품질의 유일한 지표로 삼지 않습니다. 확대 횟수, 움직임의 피로도, 클릭과 커서의 일치, 작은 글자의 선명도를 사용자 관찰로 함께 확인합니다.

혼합 DPI, 장시간 A/V, 복구, 공유 삭제는 정상 동작과 별도의 출시 차단 기준으로 둡니다. 단위 테스트 통과만으로 실제 GPU·오디오 장치 검증을 대체하지 않습니다.

## 사용자 검증의 통과 기준

5~8명의 1차 사용자가 동일한 짧은 소개 영상을 만듭니다. 진행자는 단계별 버튼을 알려주지 않고 관찰합니다.

- 녹화 대상과 소리를 잘못 선택한 지점이 있는지 기록합니다.
- 자동 결과물을 그대로 사용했는지, 어느 확대를 왜 고쳤는지 확인합니다.
- 도움 없이 MP4 또는 공유 링크를 얻었는지 확인합니다.
- 시청자에게 중요한 조작이 무엇이었는지 설명하게 합니다.
- 샘플 규모에서 나온 수치보다 반복되는 실패 원인을 먼저 해결합니다.

후속 공개 베타에서는 동의한 사용자에 한해 녹화 완료·내보내기 성공·업로드 성공 등의 집계 이벤트를 수집합니다. 영상·창 제목·입력·커서 동선은 분석용으로 전송하지 않습니다.

## 지금 확정할 수 있는 것과 남은 결정

현재 초안의 기본값은 짧은 제품 데모, Windows 11 x64, 로컬 편집, 분리된 커서, 클릭 중심 자동 확대, MP4, 공개 버전의 링크 공유입니다.

개발 착수 전에 팀의 C#·C++·React·Rust 경험을 확인해 UI 셸을 확정해야 합니다. 그 다음 Windows 10 수요, 웹캠 필요성, 일정·예산, 공유 영상 보관 기간과 운영 비용 한도를 결정하면 됩니다. 세부 슬라이더 값과 브랜드명은 핵심 엔진의 가능성 검증을 막는 결정이 아닙니다.
